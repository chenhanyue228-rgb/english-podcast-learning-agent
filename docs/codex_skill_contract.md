# Codex Skill Contract

This document defines the runtime contract between Codex and the local Python
project for English Audio Learning Agent.

It is a behavioral contract, not an implementation plan.

## 1. Contract Purpose

The project is a Codex Skill that turns podcast learning input into structured
learning artifacts and publishes them to Notion.

The contract below defines:

- what Codex is responsible for
- what Python is responsible for
- which artifacts are produced
- how those artifacts are validated
- what commands move the workflow to the next step

## 2. Architecture Rules

### User Responsibilities

The user is responsible only for actions that cannot be delegated:

- authorizing the Notion account and workspace
- creating the Notion internal connection and parent page
- adding the internal connection to the parent page
- entering the Notion token in the local hidden-input interface
- providing the complete parent-page URL
- selecting the learning source or highlighted vocabulary
- approving necessary local execution and network access

The user must not send the Notion token to Codex chat.

### Codex Responsibilities

Codex is responsible for:

- installation handoff
- user guidance
- locating or safely acquiring the complete project
- preparing and operating the local runtime
- reasoning
- language understanding
- content generation
- synthesizing learning signals into structured JSON
- advancing each workflow stage
- recovering from failures
- reporting final results

Codex must not be treated as a database writer or a deterministic parser.

### Python Responsibilities

Python is responsible for:

- orchestration
- deterministic processing
- data extraction
- validation
- file persistence
- Notion synchronization

Python must not be responsible for external LLM reasoning in the production
Skill path.

### Notion Responsibilities

Notion stores the four long-term learning databases and the final validated
knowledge assets. The production write path is the local Python Notion API
integration, not a separate Notion connector workflow.

### Local Execution Rule

Local execution is required because audio processing, transcription,
validation, configuration persistence, and Notion synchronization are
deterministic Python responsibilities.

Manual terminal operation by the user is not required. Codex should run the
local commands, prepare `.venv`, and launch the safe first-time setup tool.
Terminal instructions are a final recovery path only.

### First-Time Setup Contract

Installation uses the repository URL once. After installation, Codex continues
in the current conversation and asks whether the user wants to proceed. A new
conversation is the first Skill-refresh fallback; restarting Codex is the
second fallback.

For first-time setup, Codex:

1. verifies the complete project or safely acquires it
2. prepares the project-local runtime
3. guides the user through Notion authorization
4. launches `scripts/first_time_setup.py` or `start_setup.command`
5. keeps the access token out of chat and command arguments
6. lets Python create or validate all four databases
7. reports the result and actively asks for the first podcast

The user enters only the hidden token and complete parent-page URL in the local
interface. The user does not locate the project directory, type `cd`, edit
`.env`, extract a page ID, or run the primary workflow commands.

## 3. Stage Contracts

### 3.1 Podcast Analysis

#### Trigger

The user provides a podcast input source, such as:

- Apple Podcasts URL
- Podcast RSS URL
- Local audio file

YouTube is intentionally out of scope for v1. Experimental extraction code may
remain in the repository, but it is not part of this production contract.

The local command is:

```bash
python3 src/main.py "<source>"
```

#### Input Files

Generated by Python:

- transcript JSON under `data/transcripts/`
- AI analysis request JSON under `data/analysis_requests/`

#### Codex Responsibility

Codex reads the analysis request artifact and generates structured podcast
learning JSON from:

- prompt files
- schema files
- transcript content

#### Python Responsibility

Python:

- extracts audio
- transcribes audio
- creates the analysis request artifact
- validates the generated analysis JSON
- publishes the final Podcast Library page to Notion

#### Output Artifact

Codex-generated analysis JSON under:

```text
data/analysis/
```

Expected content includes:

- summary
- podcast metadata
- learning items
- learning notes

#### Validation Schema

Primary schema:

- `skill/schemas/ai_analysis_schema.json`

Python validation also ensures:

- required fields exist
- categories are valid
- generated JSON is well formed

#### Failure Handling

If extraction fails:

- stop before analysis generation

If analysis JSON is invalid:

- stop before Notion publish

If Notion publish fails:

- report publish failure clearly

#### Next Step Command

After Codex generates the analysis JSON:

```bash
python3 src/main.py "<source>" --analysis-json data/analysis/<file>.json
```

### 3.2 Vocabulary Enrichment

#### Trigger

Vocabulary enrichment is triggered from the vocabulary learning pipeline when
the system detects approved highlight candidates.

Current command surface includes:

```bash
python3 src/main.py --publish-highlight-vocab PAGE_ID
```

and the vocabulary learning preview / sync tools that flow into the publisher.

#### Input

Primary input:

- highlight-derived vocabulary candidate data

Supporting input:

- page context
- sentence context
- source page ID

#### Codex Responsibility

Codex is responsible for enriching the vocabulary candidate into a structured
learning record with:

- meaning
- Chinese meaning
- part of speech
- professional category
- usage example
- common collocations

#### Python Responsibility

Python is responsible for:

- collecting highlight candidates
- filtering candidates
- loading the configured provider
- validating the enrichment result
- persisting it to the Vocabulary Database

#### Output Artifact

Python writes requests to `data/vocabulary_enrichment_requests/<word>.json`.
Codex writes enriched output to `data/vocabulary_enrichment/<word>.json`. The
output matches the vocabulary schema and can then be upserted into Notion.

#### Validation Schema

Relevant schema:

- `skill/schemas/vocabulary_memory_schema.json`

Python validation ensures:

- `word` is present
- context fields are present
- `common_collocations` is normalized
- the record is structurally valid before publishing

#### Failure Handling

If enrichment fails:

- do not write partial vocabulary data
- surface a clear error

If the Notion write fails:

- report the failure without changing upstream learning data

#### Next Step Command

Once an enrichment artifact is available, publish it through the existing
vocabulary pipeline command.

### 3.3 Reflection Analysis

#### Trigger

Weekly reflection begins from the current week’s learning context.

Primary command:

```bash
python3 src/main.py --weekly-reflection
```

or the equivalent workflow command used by the pipeline.

#### Input Files

Input artifact:

- `output/weekly_learning_context.json`

#### Codex Responsibility

Codex generates a structured reflection artifact from the weekly learning
context. It must reason about:

- weekly theme
- mindset shifts
- cross-content patterns
- professional actions

#### Python Responsibility

Python is responsible for:

- loading the weekly learning context
- building the reflection request
- saving `ReflectionContext.json`
- validating the reflection output
- passing the artifact to the weekly review generator

#### Output Artifact

Reflection context artifact:

```text
output/reflection_context.json
```

Request artifact:

```text
output/reflection_context_request.json
```

Expected content includes:

- weekly_theme
- mindset_shifts
- cross_content_patterns
- professional_actions

#### Validation Schema

Relevant schema:

- `skill/schemas/reflection_context_schema.json`

Python validation ensures:

- `weekly_theme` exists and is structured
- mindset shifts are present
- evidence and confidence are valid
- reflection output is not empty

#### Failure Handling

If reflection validation fails:

- stop the workflow
- do not generate Weekly Review
- do not publish to Notion

#### Next Step Command

When reflection context is saved, continue to weekly review generation.

---

### 3.4 Weekly Review Generation

#### Trigger

Weekly review generation begins after reflection analysis succeeds.

Primary command:

```bash
python3 src/main.py --weekly-reflection
```

Optional dry run:

```bash
python3 src/main.py --weekly-reflection --dry-run
```

#### Input Files

Primary input:

- `output/reflection_context.json`

Supporting input:

- `output/weekly_learning_context.json`
- learning expressions
- user vocabulary

#### Codex Responsibility

Codex is responsible for turning reflection signals into a weekly review that
reads like a learning reflection, not a podcast summary.

Codex should produce:

- executive summary
- knowledge insights
- language growth
- career application

#### Python Responsibility

Python is responsible for:

- loading the reflection context
- loading the weekly learning context
- validating the review output
- running the quality gate
- publishing the weekly reflection page to Notion

#### Output Artifact

Weekly review artifact:

```text
output/weekly_review.json
```

Request artifact:

```text
output/weekly_review_request.json
```

Expected content includes:

- executive_summary
- knowledge_insights
- language_growth
- career_application

#### Validation Schema

Relevant schema:

- `skill/schemas/weekly_review_v2_analysis_schema.json`
- `skill/schemas/weekly_review_generator_schema.json`

Python validation ensures:

- required top-level fields are present
- reflection quality gate passes
- output is structurally valid before publish

#### Failure Handling

If generation fails:

- stop the pipeline

If quality gate fails:

- do not publish to Notion

If Notion publish fails:

- report the failure clearly and preserve generated artifacts

#### Next Step Command

If dry run is used:

```bash
python3 src/main.py --weekly-reflection --dry-run
```

If publish is allowed:

```bash
python3 src/main.py --weekly-reflection
```

## 5. Validation Rules

The Skill contract depends on strict artifact validation at each boundary.

### Podcast Analysis Validation

- transcript exists
- analysis request JSON is present
- Codex output conforms to the analysis schema
- Notion payload mapping is valid

### Vocabulary Enrichment Validation

- word is present
- context is present
- enriched metadata is present
- Notion payload is complete

### Reflection Validation

- weekly learning context exists
- reflection context includes weekly theme
- mindset shifts include evidence and confidence
- professional actions are present

### Weekly Review Validation

- weekly review output includes required sections
- quality gate passes
- publish payload matches Notion schema

## 6. Operating Principle

The Python codebase should remain deterministic and operational.
Codex should remain the reasoning engine.
Notion should remain the persistence and presentation layer.

## 7. Provider Compatibility

The production provider name is `codex` for vocabulary enrichment, reflection
analysis, and weekly review generation. A Codex provider writes a request
artifact and accepts only a current output artifact before Python validation.

The deterministic `placeholder` providers are test support. Direct OpenAI
providers are deprecated, opt-in compatibility paths and are never selected by
default. No production Skill command requires `OPENAI_API_KEY`.

That separation is the core of the Skill contract.
